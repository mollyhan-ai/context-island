# 一：总体结论

本项目技术上可行。原先的两个风险项已通过产品决策消解：

- **中文义项缺口** → 决策为「英文为主」，义项列表用 WordNet 英文释义，中文降为词级参考。
- **NLP 层部署风险** → 决策为砍掉依存交叉校验，依赖从 spaCy 换为 NLTK，体积风险随之消失。

第二项削弱了 PRD 约束八，已附补偿措施（主干成分准确率提为上线阻断项）。

除此之外，技术选型基本采用手册的 B 类默认方案，偏离处逐条说明。

# 二：语言与框架选型

| 层 | 选型 | 类别 | 说明 |
| --- | --- | --- | --- |
| 后端语言 | Python 3.11 | B 类默认 | 采用。NLP 生态在 Python 侧最成熟，本项目强依赖 |
| 后端框架 | FastAPI | B 类默认 | 采用 |
| 数据校验 | Pydantic v2 | B 类默认 | 采用。模型输出的结构校验强依赖它 |
| 测试 | pytest | B 类默认 | 采用 |
| 前端框架 | Next.js（App Router）+ TypeScript | B 类默认 | 采用 |
| 样式 | Tailwind CSS | B 类默认 | 采用 |
| 数据存储 | SQLite | B 类默认 | **分两类使用，见第四节** |
| ORM | 不使用 SQLAlchemy | **偏离 C 类** | 见下 |
| 向量库 | 不使用 | C 类不选 | 本产品无 RAG 需求，词库是精确查询不是语义检索 |
| OCR | 不使用 | C 类不选 | 无图像输入 |
| SSE / 流式 | 不使用 | C 类不选 | 见下 |

## 偏离说明

**不使用 SQLAlchemy。** 词库是只读的、结构固定的两三张表，查询模式只有"按单词取义项"一种。引入 ORM 增加依赖体积（这在 veFaaS 上是稀缺资源，见第九节）而不带来收益。用标准库 `sqlite3` 直接查询，配合 Pydantic 做出参建模。用户侧数据（生词本）表结构同样简单，一并直连。

**影响：** 后续如果生词本演化出复杂关联查询，需要重新评估。本期范围内不会发生（PRD 约束六限定生词本只有保存和再生成两个动作）。

**不使用流式输出。** PRD 的输出是一个必须整体校验的 JSON（5.2 输出结构契约：segments 拼接必须与 sentence 完全一致）。流式吐出会让校验无法进行，且卡片是一次性渲染的结构化内容，不是逐字阅读的长文。

**影响：** 用户在 P95 约 8 秒内看不到中间内容，需要前端提供明确的等待反馈（PRD 5.5 已要求）。

# 四：数据存储方案

分两类，因为 veFaaS 的读写限制（部署手册：`/tmp` 之外只读）。

## 4.1 词库：只读，随部署包发布

`lexicon.db` 在**构建阶段生成**，作为静态资源打进部署包，运行时只读。实例回收不影响它。

表结构：

| 表 | 内容 |
| --- | --- |
| `word` | 词形、词频秩、难度档、音标、音频 URL |
| `sense` | synset 编号、词性、英文释义、义项使用频次、中文释义 |
| `word_sense` | 词与义项的关联 |
| `realm_word` | 领域常见词（六个领域各 12 词，人工整理） |

`sense.synset` 即 PRD 的 sense_id，全局唯一且稳定。

## 4.2 用户数据：可写，需备份恢复

生词本写在 `/tmp/user.db`。按部署手册的轻量方案：**预留实例 + 定期备份至 TOS + 启动时自动恢复**。

**风险提示：** 这套方案在实例被回收到重新拉起之间存在数据窗口。对本产品可接受（生词本丢失不致命），但**不可用于任何有更强持久性要求的数据**。阶段四实现时需要验证恢复流程真的能跑通，不能只写不测。

# 五：词库方案（问题 1）

## 5.1 本地化方式

两个数据源都在**构建阶段**处理完毕，运行时不联网、不调外部服务：

| 源 | 用途 | 处理方式 |
| --- | --- | --- |
| WordNet | 义项划分与 synset 编号、英文释义、义项频次 | 通过 NLTK 的 wordnet 语料下载，构建脚本导出为 SQLite |
| ECDICT | 词频秩（BNC/COCA）、中文参考释义 | CSV 导入 SQLite |
| Free Dictionary API | 音标、真人录音 URL | 构建阶段批量预取常见词，其余运行时按需拉取并缓存 |

**合规执行**（PRD 5.4.2）：两个 LICENSE 文件随仓库保存；页脚标注数据来源与 WordNet 官方引用；README 写明许可类型；不使用普林斯顿名义背书；不导入 ECDICT 的牛津 3000、柯林斯星级、考纲标注字段。

## 5.2 中文处理：英文为主（已决策）

**产品经理决策：方案 A，义项列表用 WordNet 英文释义，中文不与义项对齐。**

原因：WordNet 的 synset 是英文义项；ECDICT 的中文释义是按词合并的整串文本，不是按义项拆分的条目。两者之间**没有现成的一一映射**，自动构建会产生错误对应。

因此实现如下：

| 展示位 | 数据来源 | 说明 |
| --- | --- | --- |
| 义项列表 | WordNet 英文释义 | 命中项高亮，sense_id 即 synset 编号 |
| 词级中文参考 | ECDICT | 单独一栏，页面需标注为整词参考、不对应具体义项 |
| 例句整句翻译 | 模型生成 | 不受影响 |

**构建脚本因此变简单**：不需要做跨语言对齐，`sense` 表的中文字段留空，中文只在 `word` 表存一份。

**连带影响已回写 PRD 5.4.1**：卡片形态与早期原型不同；A2 档位可能因英文释义可读性问题需要在阶段一后砍掉。

## 5.3 300ms 性能

只读 SQLite + `word` 表词形字段唯一索引 + `word_sense` 联合索引，单词查询在本地是亚毫秒级。300ms 的实际风险不在查询本身，而在 **veFaaS 冷启动**（见第九节）。热实例下这个指标没有压力。

# 六：NLP 层选型（问题 2）—— 本项目最大技术风险

## 6.1 选型（已按决策调整）

**NLTK**，Apache 2.0 许可，允许商用。提供三样本项目需要的能力：

| 能力 | NLTK 组件 | 用途 |
| --- | --- | --- |
| WordNet 语料 | `nltk.corpus.wordnet` | 义项划分与 synset 编号（第五节） |
| 词性标注 | 感知机标注器 | 约束八第一条 |
| 词形还原 | `WordNetLemmatizer` | 难度校验前的还原（第九节） |

**原选型 spaCy 已放弃。** 原因不是能力不足，而是它唯一的独占价值——依存句法分析——在本期已被砍掉（见 6.2）。保留 spaCy 只为词性标注，等于为一个轻量任务背上数十至上百 MB 的依赖，与 veFaaS 的部署约束冲突。

**换用 NLTK 的连带收益：** WordNet 语料本来就要通过 NLTK 获取，现在词库、词性、词形还原共用同一个依赖，依赖链显著收窄，部署包体积风险基本消除。

**仍需在阶段一第一天实测：** NLTK 加 WordNet 语料的实际体积与冷启动耗时。风险等级已从"可能翻车"降为"例行确认"，但数字仍要拿出来，不靠估计。

## 6.2 依存交叉校验：本期不做（产品经理已批准）

PRD 约束八原定引入依存句法分析，与模型的成分标注做交叉校验。**产品经理决策：本期砍掉，降级为 P2。**

**失去的：** 每张卡片的主谓宾标注不再有第二信源逐条互证。原本这是自动化的、全量的；现在只剩评测集，是抽样的、发版时才跑的。

**补偿措施（已写入 PRD 第七节）：** 「主干成分准确率」由一般指标提升为**上线阻断项**。这是本次降级的交换条件，实施时不得省略。

**已知限制（建议对外如实说明，不要隐瞒）：** 成分标注的准确率保障从"自动校验 + 评测集"变为"仅评测集"。

## 6.3 词性标签的呈现

NLTK 的标注结果为 Penn Treebank 标签集（`NN`、`VBD`、`JJ` 等），需映射为面向学习者的简写（`n.`、`v.`、`adj.`、`adv.`、`pron.`、`prep.` 等），映射表作为静态配置维护，不由模型决定。

由于不再做交叉校验，**PRD 5.1 的句子成分标签与 NLP 输出之间不存在映射需求**，原声明中的 UD 标签映射表已删除。

# 七：校验引擎的可测试性（问题 3）

## 7.1 纯函数设计

> 本期为**四道校验**。原第 6 道依存交叉校验已按决策砍掉（见 6.2）。

四道校验全部实现为**无副作用的纯函数**，签名形如：

```
validate_xxx(model_output: CardDraft, context: ValidationContext) -> ValidationResult
```

- `CardDraft` 是 Pydantic 模型，由 JSON 解析得到，**不含任何模型客户端引用**
- `ValidationContext` 包含该词的义项集合、词频表、目标难度、NLP 分析结果——全部是可构造的普通数据
- `ValidationResult` 返回通过与否、失败原因码、是否触发降级

**关键点：`validators/` 目录下不导入任何 LLM SDK。** 这是可以用 import 检查强制的，建议加一条测试断言它。

## 7.2 mock 测试覆盖

| 校验 | 测试方式 | 关键用例 |
| --- | --- | --- |
| 1 片段拼接一致 | 纯函数 | 漏标一个词、改写标点、多加空格、大小写变化 |
| 2 sense_id 存在 | 纯函数 + 构造义项集合 | 返回不存在的编号、返回空、返回其他词的编号 |
| 3 标签在集合内 | 纯函数 | 返回集合外术语、第二层标签用了第一层的值 |
| 4 唯一目标片段 | 纯函数 | 零个、两个、目标词被拆到两个片段 |
| 5 难度校验 | 纯函数 + 构造词频表 | 超纲词恰好 1 个、恰好 2 个、句长边界值 |

外加**解析器容错测试**：模型输出被 Markdown 代码块包裹、JSON 前后带解释文字、字段顺序打乱、多余字段。手册第九节要求解析器兼容多种等价格式，这部分必须有专门用例。

**再加状态机测试**：重试计数、达到上限后转降级、降级卡片仍返回内容而非报错。

以上全部**离线可跑，不需要模型 Key**。真实模型冒烟测试单独放在 `test_smoke_real.py`，用 pytest 标记隔离，**不得混入常规测试套件冒充自动化验收**（手册 A 类底线）。

# 八：发音音源（问题 4）

## 8.1 接入与缓存

分两个时机：

- **构建阶段预取**：六个领域各 12 词，共 72 个词，加上八张样卡的词，构建时批量拉取音标与音频 URL 写入 `lexicon.db`。这批词是用户最可能点的，预取后零延迟。
- **运行时按需**：用户查询预取范围外的词时调用 Free Dictionary API，结果写入 `/tmp` 缓存。实例回收后缓存丢失，会重新拉取，可接受。

## 8.2 判空逻辑放在后端

**判空必须在后端完成，不能交给前端。**

后端返回卡片数据时，`audio` 字段要么是可用 URL，要么是 `null`。前端只做一件事：`audio` 为 null 就不渲染按钮。

理由：约束九是产品硬约束，把判断放在前端意味着任何一个前端 bug 都会让约束失效。放在后端，约束由数据结构本身保证。

## 8.3 两个必须提出的风险

**风险一：音频 URL 是外链。** Free Dictionary API 返回的音频指向第三方存储，不是我们的资源。如果对方变更或失效，发音功能会静默损坏。

建议：加一个可用性探测，或者长期考虑把常用词音频镜像到自己的对象存储——但后者需要确认这些录音本身的授权是否允许再分发，**这一点我无法确认，需要在做镜像之前查清楚**。本期不做镜像。

**风险二：该 API 是社区免费服务，无 SLA。** 运行时按需调用必须设超时与失败兜底：拉取失败时按约束九不显示按钮，而不是让卡片生成失败。

# 九：难度分级近似（问题 5）

## 9.1 数据与分档

使用 ECDICT 自带的 **BNC 与 COCA 词频秩**。取两者中较宽松的一个作为该词的难度判据（避免单一语料的偏差把常用词误判为超纲）。

| 档位 | 词频秩范围 | 句长上限（PRD 约束二） |
| --- | --- | --- |
| A2 | 前 2000 | ≤ 12 词 |
| B1 | 前 4000 | ≤ 18 词 |
| B2 | 前 8000 | ≤ 25 词 |

分档阈值在阶段二首轮评测后可调整，调整需记录并重跑回归。

## 9.2 已知偏差 —— 必须显式记录

**这是一个近似，不是 CEFR。以下偏差是已知的、不打算在本期解决的：**

1. **词频不等于难度。** `get`、`take`、`put` 词频极高但短语动词用法对学习者很难；`hippopotamus` 词频低但完全不构成理解障碍。
2. **多义词被单一秩代表。** 一个词的常见义项简单、罕见义项难，但词频秩只有一个数字。
3. **与领域词汇天然冲突。** 这是本产品特有的问题：`indemnity`、`contraindication` 在通用语料中词频很低，但它们正是领域常见词表里的核心词。PRD 约束二写的是"除目标词外"，所以目标词本身不受影响；**但如果生成的句子里出现第二个领域术语，会被误判为超纲并触发重生成**，可能导致降级率偏高。
4. **词形还原影响判定。** 需在校验前做 lemmatization，否则 `matured` 查不到 `mature` 的词频。使用 NLTK 的 `WordNetLemmatizer`，与词库共用同一依赖。

**针对第 3 点的处理：** 建议在难度校验时，对当前领域词表内的词给予豁免（视同不超纲）。这是一个产品决策而非技术决策，列入第十节问题 C。

# 十二：日志与错误处理

- 统一异常兜底，任何未捕获异常返回结构化错误，不向前端泄漏堆栈
- **日志不记录 API Key、不记录完整 Prompt**（可记录 Prompt 版本号）
- 每张卡片记录：耗时、重试次数、各道校验的通过情况、是否降级、降级原因码
- 降级原因码是可枚举的固定集合，便于阶段二统计降级率分布并定位 Prompt 问题
- 外部服务（模型、词典 API）调用统一设超时，失败不阻断主流程
