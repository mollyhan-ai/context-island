# 三：词库构建

## 3.1 设计原则

**构建脚本 `data/build_lexicon.py` 离线运行，产出物随部署包发布，运行时只读。**

运行时**不依赖 NLTK 的 WordNet 语料**，所有义项数据已展平进 SQLite。运行时的 NLTK 只用于词性标注与词形还原。

构建脚本必须**幂等**：重复运行产出一致的数据库，不追加重复行。

## 3.2 表结构

```sql
-- 词
CREATE TABLE word (
  lemma        TEXT PRIMARY KEY,   -- 原形，小写
  freq_bnc     INTEGER,            -- BNC 词频秩，缺失为 NULL
  freq_coca    INTEGER,            -- COCA 词频秩，缺失为 NULL
  level        TEXT,               -- A2 / B1 / B2 / OTHER，阶段二使用
  zh_gloss     TEXT                -- ECDICT 整词中文参考，不对应具体义项
);

-- 义项
CREATE TABLE sense (
  sense_id     TEXT PRIMARY KEY,   -- WordNet synset 名称，如 'exposure.n.01'
  pos          TEXT,               -- n / v / adj / adv
  definition   TEXT NOT NULL,      -- WordNet 英文释义
  examples     TEXT,               -- WordNet 自带例句，JSON 数组，可空
  sense_rank   INTEGER             -- 该义项在所属词内的使用频次排序，1 最常用
);

-- 词与义项关联
CREATE TABLE word_sense (
  lemma        TEXT NOT NULL,
  sense_id     TEXT NOT NULL,
  PRIMARY KEY (lemma, sense_id)
);

CREATE INDEX idx_word_sense_lemma ON word_sense(lemma);
```

**注意 `sense.definition` 是英文**，按 PRD 5.4.1 决策。`sense` 表没有中文字段，中文只在 `word.zh_gloss` 存一份整词参考。

`sense_rank` 来自 WordNet 的义项计数，是 5.4.3 义项截断方案的排序依据。

## 3.3 构建步骤

1. 读 WordNet，遍历目标词表，导出 synset、释义、例句、义项频次
2. 读 ECDICT CSV，取 lemma、BNC 秩、COCA 秩、中文释义
3. 合并写入 SQLite，建索引
4. 输出构建报告：词数、义项数、有中文的词占比、无词频数据的词占比

**目标词表范围（阶段一）：** 不需要全量词库。取 ECDICT 中 COCA 秩前 10000 的词即可，覆盖本阶段验证需求，控制体积。全量导入放到阶段三。

## 3.4 许可合规（PRD 5.4.2，构建时一并落实）

- WordNet 与 ECDICT 的 LICENSE 文件复制进仓库
- README 写明数据来源与许可类型
- **不导入 ECDICT 的牛津 3000、柯林斯星级、考纲标注字段**
- 不使用普林斯顿名义背书（本阶段无前端文案，阶段三落实页脚署名）

# 四：数据模型

Pydantic v2，放 `models/`。

```
Sense          sense_id, pos, definition, examples, sense_rank
WordEntry      lemma, senses[Sense], zh_gloss, freq_bnc, freq_coca

Segment        text, layer1, layer2|None, is_target, note|None, pos|None
CardDraft      sentence, sense_id, translation, segments[Segment], ambiguity|None
Card           = CardDraft + 回填的 sense 详情、词性、生成元信息

ValidationContext   word_entry, target_lemma, allowed_tags, nlp_result
ValidationResult    passed: bool, code: str|None, detail: str|None
```

**`CardDraft` 是模型输出的直接映射，`Card` 是回填后的对外结构。** 两者分开，是为了让校验只面对 `CardDraft`，不被回填数据污染。

`Segment.pos` 在模型输出时为 `None`，由 NLP 层在校验后填入（约束八）。

# 五：接口设计

阶段一只需三个，均为后端接口。

```
GET  /api/word/{lemma}
     → WordEntry；词库无此词返回 404 且 code=WORD_NOT_FOUND
     （PRD 5.4.5：不得转由模型生成释义）

POST /api/card
     body: { word: str, realm: str, level: str }
     → Card | 失败结构
     
GET  /health
     → 依赖自检：词库可读、NLTK 可用、模型配置存在
```

**`/api/card` 的失败结构必须结构化**，不返回堆栈：

```json
{ "ok": false, "code": "VALIDATION_EXHAUSTED", "detail": "…", "attempts": 3 }
```

## 错误码（固定枚举，阶段二统计降级率时复用）

| code | 含义 |
| --- | --- |
| `WORD_NOT_FOUND` | 词库无此词 |
| `MODEL_TIMEOUT` | 模型调用超时 |
| `MODEL_ERROR` | 模型返回异常 |
| `PARSE_FAILED` | JSON 无法解析 |
| `SEG_MISMATCH` | 片段拼接与原句不一致（校验 1） |
| `SENSE_INVALID` | sense_id 不在该词义项集合内（校验 2） |
| `TAG_INVALID` | 标签不在集合内（校验 3） |
| `TARGET_INVALID` | 目标片段数量不为 1（校验 4） |
| `VALIDATION_EXHAUSTED` | 重试耗尽仍未通过 |

# 六：模型调用与 Prompt 管理

## 6.1 Prompt 独立文件

```
core/prompts/
├── card_v1.md          # PRD 5.3 的 Prompt 模板
└── grammar_spec.md     # PRD 5.1 标签体系，作为变量注入
```

**Prompt 以文件形式管理，可版本追踪。** 修改 Prompt 视为需要回归的变更（PRD 7.4）。

日志记录 Prompt 版本号，**不记录完整 Prompt 内容，不记录 API Key**。

## 6.2 调用参数

- 超时必设，建议 30 秒
- 温度设低值，本任务要的是稳定不是创意
- 要求 JSON 输出（若模型支持结构化输出模式则启用，视为降低解析失败率的手段，不替代解析器容错）

## 6.3 重试策略

重试上限 3 次（PRD 约束二、5.2）。

**重试时把上一次的失败原因加进 Prompt**，而不是原样重发——原样重发大概率得到同样的错误输出。

# 七：解析器设计

手册第九节要求解析器兼容多种等价格式。必须处理：

1. 输出被 ` ```json ` 代码块包裹
2. JSON 前后带解释文字
3. 字段顺序与文档不同
4. 出现文档未定义的多余字段（忽略，不报错）
5. 中英文标点混用（如全角引号）

**解析器是纯函数，输入 str 输出 `CardDraft | ParseError`，必须有独立单测。**

不做的事：不尝试修复结构性错误的 JSON。解析失败就是 `PARSE_FAILED`，走重试。

# 八：校验引擎

## 8.1 阶段一实现三道

| 序号 | 模块 | 规则 |
| --- | --- | --- |
| 1 | `validators/structure.py` | `segments` 的 `text` 按序拼接后，与 `sentence` 完全一致 |
| 2 | `validators/sense.py` | `sense_id` 存在于该 lemma 的义项集合中 |
| 3 | `validators/structure.py` | `layer1` 在七个第一层标签内；`layer2` 为空或在七个第二层标签内 |
| 4 | `validators/structure.py` | 有且仅有一个 segment 的 `is_target` 为真 |

难度校验（校验 5）在阶段二实现，本阶段留出接口位置但不启用。

## 8.2 拼接一致性的判定细节

这一条最容易出歧义，明确如下：

- 拼接时**按 segments 顺序,用单个空格连接**，然后与 `sentence` 做规范化比较
- 规范化：合并连续空白、统一撇号与引号的全半角、**不忽略大小写**、**不忽略标点**
- 若模型把标点单独切成一个 segment，允许通过（标点归属不做强制）

**大小写和标点必须严格**，因为约束一的实质是"模型不得改写原句"，放宽这两项等于给改写开口子。

## 8.3 硬性约束

**`validators/` 目录下任何模块不得 import 模型客户端。**

加一条测试断言这件事：遍历该目录所有模块的 import，出现模型 SDK 即失败。这条测试本身就是约束的执行机制。

# 九：状态机

```
idle → generating → (parse) → (validate) 
                                 ├─ pass → succeeded
                                 ├─ fail & attempts<3 → generating
                                 └─ fail & attempts=3 → failed
```

阶段一**没有降级态**（降级属于阶段二），校验耗尽即 `failed` 并返回 `VALIDATION_EXHAUSTED`。

每次尝试记录：耗时、失败码、重试序号。这些字段阶段二直接复用于降级率统计。

# 十：最小验收界面

## 10.1 定位

**这不是产品界面，是验收工具。** 它的唯一职责是让人用眼睛判断卡片质量，尤其是成分树。阶段三会被正式前端完全替换。

不投入视觉设计，不做响应式，不做状态动效。

## 10.2 内容

- 三个输入：单词、领域、难度档
- 一个生成按钮
- 结果区：例句、整句翻译、成分树（层级可见、目标片段可辨、词性可见）、英文义项列表（命中项标出）、整词中文参考
- **调试区（这是验收界面的关键部分）**：本次重试次数、每次尝试的失败码、总耗时、模型原始输出

调试区不能省。没有它，看到一张错卡也不知道错在哪一环。

## 10.3 技术

单文件即可，不引入前端工程。由 FastAPI 直接返回一个静态页面。

# 十二：义项粒度验证（PRD 5.4.3）

阶段一必须完成，产出一份简短报告。

## 方法

取 20 个 B1 常见多义词（如 run、set、light、charge、address、issue、subject、matter、mean、bear…），对每个词记录：

1. WordNet 义项总数
2. 前 5 条义项是否覆盖了日常主要用法
3. 英文释义对 A2 学习者的可读性（主观判断，标注理由）

## 判定

- **义项数中位数 > 6** → 需要做义项合并或截断，给出方案建议
- **A2 可读性不可接受** → 建议本期收敛为 B1/B2 两档，提请产品经理决策

## 产出

`docs/义项粒度验证报告.md`，含数据表与结论。

## 提前暴露的风险

例如某些释义会用到比被解释词更难的词。这个问题在义项粒度验证时会一并显现，但**它可能比义项数量更影响 A2/B1 的可用性**。如果验证结果不乐观，可选方案有：优先展示 WordNet 自带例句而非释义、或对释义做离线简化改写（同 5.2 方案 C 的性质，需另行决策）。

**现在不需要决定，但请对这个风险有预期。**
